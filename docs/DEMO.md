# Сценарий демонстрации для жюри

> Важно: `docs/demo-requirements.md` — это **тестовый** документ с намеренно
> заложенными дефектами, созданный только для демонстрации возможностей агента.
> Финальный конкурсный отчёт должен быть сформирован на реальном документе
> требований организаторов хакатона (см. `reports/organizer-analysis.md`,
> который создаётся отдельной командой после получения документа организаторов).

## 1. Что показать (2–3 минуты)

1. Запустить backend и CLI-анализ демонстрационного документа одной командой.
2. Открыть веб-интерфейс, загрузить тот же документ через drag-and-drop.
3. Показать реальный прогресс анализа (этапы бэкенда, а не анимацию).
4. Показать дашборд: Health Score, вердикт, распределение по серьёзности.
5. Открыть вкладку «Требования», показать REQ-2 («работать быстро») —
   замечание с точной цитатой, объяснением и примером улучшенной формулировки.
6. Открыть вкладку «Анализ набора» → «Противоречия»: показать конфликт
   REQ-3 (2 секунды) vs REQ-4 (10 секунд) с цитатами обеих сторон.
7. Показать дубликат REQ-5 / REQ-6 (кнопка «Выход» и «Завершить сеанс»).
8. Скачать Markdown- и JSON-отчёт.

## 2. Команды запуска

### CLI (один документ → один отчёт)

```bash
cd cream_ai
cp .env.example .env   # указать GEMINI_API_KEY
./mvnw spring-boot:run -Dspring-boot.run.arguments="--input=../docs/demo-requirements.md --output=reports/demo-result.md"
```

### Backend + Frontend (веб-интерфейс)

```bash
# Терминал 1
cd cream_ai
./mvnw spring-boot:run

# Терминал 2
cd frontend
npm install
npm run dev
# открыть http://localhost:5173
```

## 3. Ожидаемый результат (кратко)

- Health Score существенно ниже 100 (не идеальный документ).
- Вердикт: `NOT_READY` или `READY_WITH_RESERVATIONS` (нет подтверждённых CRITICAL,
  но есть HIGH-противоречие REQ-3/REQ-4 и системная проблема ролей REQ-10/REQ-11).
- Минимум одно подтверждённое противоречие (REQ-3 ⟷ REQ-4).
- Минимум один подтверждённый дубликат (REQ-5 ⟷ REQ-6).
- Замечания по REQ-2 и REQ-8 (неизмеримые формулировки «быстро», «надёжной»).
- Системное замечание о несогласованности ролей: REQ-11 (полный доступ
  администратора без подтверждения) против REQ-10 (обязательное SMS-подтверждение
  крупных операций).
- REQ-1, REQ-7, REQ-9 — качественные требования без значимых замечаний.

## 4. Сильные стороны продукта

- **Evidence-First Architecture**: каждое замечание — это цитата + страница/строка +
  статус доказательности (CONFIRMED_ISSUE / POTENTIAL_ISSUE / NEEDS_HUMAN_REVIEW),
  а не просто мнение модели.
- **Отдельный этап верификации** после LLM: цитаты проверяются на соответствие
  исходному документу, а не принимаются на веру.
- **Contradiction Detective**: явный механизм поиска противоречий с цитатами
  обеих сторон и предложением разрешения.
- **Health Score с прозрачной расшифровкой**: видно, из чего складывается балл,
  а не только итоговое число.
- **False Positive Protection**: серьёзность не завышается для непроверенных
  замечаний; статус «требует проверки человеком», если доказательства недостаточно.
- **CLI + REST API + веб-интерфейс** на одном и том же конвейере анализа —
  никакой логики не продублировано.

## 5. Архитектура (коротко)

```
Документ → DocumentParser → RequirementExtractor (LLM) → RequirementNormalizer
   → IndividualRequirementAnalyzer (LLM, критерии ISO 29148 / IEEE 830)
   → RequirementSetAnalyzer (LLM, противоречия/дубликаты/пробелы)
   → ContradictionDetector → EvidenceVerifier → SeverityClassifier
   → RequirementScorer (Health Score) → TraceabilityAnalyzer → VerdictCalculator
   → MarkdownReportGenerator / JsonReportWriter
```

`LLMProvider` — интерфейс; `GeminiLLMProvider` — единственная реализация сейчас,
но Gemini можно заменить другим провайдером без изменения остальной системы.

## 6. Методика оценки (Health Score)

Score = (среднее качество по критериям ISO/IEEE) − (штраф за системные проблемы
набора) × (коэффициент доказанности замечаний). Это собственная прозрачная
методика продукта, не официальная оценка ISO — расшифровка всегда приводится
в отчёте (раздел «Requirement Health Score»).
